# Как добавить своё правило в каталог

Каталог живёт в карточках `catalog/<код>-<тег>.md`. Всё остальное (`reference.md` для скилла, индексы, таблица тегов) собирается из них. Правка каталога это всегда три шага: карточка, пример, прогон.

## 1. Карточка

Скопируйте любую карточку, например `A3-yes-no-gate.md`. В шапке: код (следующий свободный номер в группе A, B, C или D), тег латиницей через дефис, группа, названия на двух языках. Ниже две секции, `## RU` и `## EN`, обе обязательны. В каждой четыре абзаца:

- **Что это.** Как ошибка выглядит в скрининге.
- **Что ломается.** Чем за неё платят в поле: кто проходит лишний, кого банят, на что жалуется заказчик. Если на этот вопрос нет ответа, правило в каталог не попадает.
- **Как чинить.** Конкретная замена, а не совет «сделать лучше».
- **Исключения.** Когда похожая конструкция ошибкой не является.

Пример «плохо» и «хорошо» в виде вопроса с вариантами и логикой, как в редакторе.

## 2. Пример для проверки

В `evals/drafts/` положите черновик скрининга с этой ошибкой. Лучше всего обезличенный двойник реального: клиент и бренды заменены, структура, логика и квоты сохранены. Формат тот же, что у остальных черновиков: вопросы, варианты, тип, рандомизация, логика словами, квоты, краткое тело анкеты.

В `evals/cases/` опишите ожидания:

```yaml
- description: "коротко, что внутри и что должно найтись"
  vars:
    draft: file://drafts/my-case.md
    expect: "my-new-tag@S3"            # что скилл обязан найти (несколько через запятую, одной строкой)
    reject: "overlap@S1"               # известные ложные тревоги, которых быть не должно
    tolerate: "no-randomization@S3"    # допустимые дополнительные находки
    maxExtra: 3                      # сколько прочих лишних находок терпим
    mustKeep: "Лимонн"                 # что должно остаться в исправленном скринере (квотные вопросы, варианты)
  assert:
    - { type: javascript, value: "file://lib/tags.mjs:expectTags", weight: 3 }
    - { type: javascript, value: "file://lib/tags.mjs:rejectTags", weight: 2 }
    - { type: javascript, value: "file://lib/tags.mjs:limitExtras", weight: 1 }
    - { type: javascript, value: "file://lib/harm.mjs:keepsQuotaQuestions", weight: 2 }
```

Если правило сужает старое (например, «это не ошибка, если…»), добавьте ещё и ловушку: черновик, где старая версия правила сработала бы зря, с этим тегом в `reject`.

## 3. Прогон

Из корня репозитория:

```bash
npm run catalog:build      # пересобрать reference.md, индексы и таблицу тегов из карточек
npm test                   # структурная проверка: у карточки обе секции, тег совпадает, кейсы ссылаются на существующие коды
npm run eval:screener      # прогон всех примеров через модель, по три раза каждый
npm run eval:view          # отчёт в браузере: ответ модели и вердикт каждой проверки
```

Сравните с `evals/results/baseline.md`. Новый пример должен проходить стабильно, старые не должны упасть. Если упали, значит правило конфликтует с другим, и это надо решить в карточках, а не в примерах.

Коды ошибок (A6, C1) видны только здесь. Человек в ответе скилла читает ошибку словами, машинная строка тегов появляется только в прогонах.
